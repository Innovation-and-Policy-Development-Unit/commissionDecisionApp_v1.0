## What's already conformant (confirmed, not assumed)

- **Form labels (1.3.1, 4.1.2):** `BaseInput.jsx` and `BasePasswordInput.jsx` (both read in full) correctly use `useId()`-bound `<label htmlFor>`, `aria-invalid`, and a labeled password-visibility toggle. `Login.jsx` uses these primitives with real `label=` props throughout, not placeholder-only text. No gap found in either primitive or its usage on the highest-traffic auth screen.
- **CORS/CSP as an accessibility-adjacent concern:** not applicable here, covered in the security assessment.
- **Design tokens for typography/color scale:** a genuine token system exists in `tailwind.config.js` (color scale, type scale, shadows), which is the right foundation for consistent, auditable contrast ratios going forward — though per-component contrast was not individually measured in this pass (flag as a follow-up: a systematic contrast audit against the actual rendered `primary`/`slate` combinations in both light and dark themes).

## Not assessed in this pass (recommend as follow-up)

- Live contrast-ratio measurement (WCAG 1.4.3/1.4.11) against actual rendered colors in both themes — the token system exists but ratios weren't individually measured.
- Screen-reader announcement of workflow-state changes (e.g. does a submission's stage change get announced via a live region when it happens without a full page navigation?) — `components/shared/LiveRegion.jsx` exists in the shared component library, indicating the pattern is known and used somewhere; whether it's wired to every state-change surface wasn't traced.
- A full runtime pass with an actual screen reader (NVDA/VoiceOver) against the three flagship screens — this review is a static-code audit; several of the `UNVERIFIED` items above specifically need this.
